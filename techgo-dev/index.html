保守と改修が中心なのは、

経済産業省が2018年に公表した「DXレポート」は、日本企業のITの課題として「2025年の崖」を提起しました。その中身は要するに、既存システムを維持し続けることに、資金と人材が大きく割かれているという指摘です。

そして、この状況は今も続いています。

野村総合研究所が2025年9月に実施した「IT活用実態調査（2025年）」では、情報システムにレガシーシステムが存在すると回答した企業は、アプリケーションで47.3%、基盤で48.2%。つまり、約半数の企業に、まだ古いシステムが残っているということです。

さらにIPA「DX動向2025」では、DXを推進する人材の“量”が不足していると回答した日本企業は85.1%。米国の23.8%、ドイツの44.6%と比べても高い水準でした。

  2. ソフトウェア開発スペシャリスト450〜695万円

Branch

同じJava・同じPythonでも、
経験の中身はここまで分かれます

ここまでの話を、もう少し具体的にします。

Java の場合

A：すでに動いているものを、止めないための開発
  • 既存の基幹系・業務系システムの改修と障害対応
  • フレームワーク、バージョン、設計方針は着任前から決まっている
  • 詳細設計書に沿った実装と、テストエビデンスの作成が中心
  • 身につくもの：既存仕様の読解力、影響範囲の見極め、障害対応の胆力
/ /
B：これから作るもの、作り替えるものの開発
  • レガシー刷新・マイクロサービス化・クラウド移行
  • 技術選定やアーキテクチャの議論に参加する
  • 事業側と要件を詰める場面がある
  • 身につくもの：設計判断の理由を言語化する力、技術選定の経験、上流の視点

どちらも価値のある仕事です。

ただし、転職市場で「次に何ができる人か」を判断するときに参照されやすいのはBの経験です。そしてAにいる人の多くが、実はB寄りの経験も部分的に持っています（後述）。

Python の場合

A：業務を回すためのPython
  • 社内の定型作業の自動化、Excel連携、定期バッチ、簡易スクレイピング
  • 「Pythonができる人」として便利に頼まれる
  • 使うライブラリの範囲が固定されがち
/ /
B：プロダクトや意思決定を支えるPython
  • データ基盤の構築・整備、ETL、分析用パイプライン
  • 機械学習モデルの実装・運用、MLOps
  • SaaSプロダクトのバックエンド、API開発

同じ「Python 3年」でも、AとBでは職務経歴書に書ける内容がまったく変わります。

そして重要なのはここです。AにいるからBに行けない、という決まりはありません。Aで培った「業務理解」「泥臭いデータの扱い」「現場の要件を聞き取る力」は、Bの現場でも評価対象になります。

問題は、
その経験が“B側の言葉”で書かれていないことです。
Data · 03

経験が足りないのではなく、
足りている場所に立っていないだけかもしれません

需要は、IT業界の中で均等に分布していません。

経済産業省の委託調査「IT人材需給に関する調査」（2019年3月公表）では、IT需要の伸びが高位で推移した場合、2030年に先端IT人材は約54.5万人不足する一方、従来型IT人材は約9.7万人が余るという試算が示されています。IT人材全体では、2030年に最大で約79万人が不足するとされました。

厚生労働省の「job tag」に掲載されている有効求人倍率（令和6年度）を見ても、同じIT系の職業の中で数字が大きく違います。

有効求人倍率（令和6年度）

  1. プログラマー0.94倍
  2. データサイエンティスト11.88倍

ハローワークに登録された求人が母集団のため、転職市場全体を示すものではありません。それでも、同じIT職の中に需給の温度差があることは読み取れます。

さらに、企業側の動きも変わってきています。野村総合研究所「IT活用実態調査（2025年）」では、生成AIを導入済みの企業は57.7%、検討中を含めると約76%。新しい技術を実際に扱える人を必要とする企業は、確実に増えています。

つまり——

「経験が足りない」のではなく、
「経験が足りている場所に、
まだ立っていない」。 このズレは、努力量ではなく、情報量で埋められる部分があります。

求人票には、たいてい同じようなことが書かれています。

job_posting.txt

- 実務経験3年以上
- 要件定義から携われます
- モダンな開発環境

ここから読み取れないことのほうが、実は多いのです。

// 求人票に書かれていないこと

  • ?そのプロダクトは、会社の売上のどこに位置しているのか
  • ?開発は内製なのか、外部に出しているのか
  • ?技術選定の権限は、どのポジションにあるのか
  • ?「要件定義から」は、実際にはどこまでを指しているのか
  • ?レガシー刷新の途中なのか、すでに終わっているのか

同じ求人票でも、この中身によって、3年後に自分が何を語れる人になるかが変わります。

そしてこれは、求人票を何百件読んでも書いていません。その会社を見てきた人からしか、出てこない情報です。

Problem · 02

経験者が損をする一番の原因は、
職務経歴書が「使用言語の一覧」に
なっていること

転職に慣れていないエンジニアの職務経歴書は、こうなりがちです。

resume.md
【使用言語】 Java, SQL, Shell
【担当工程】 詳細設計、製造、単体テスト
【業務内容】 既存システムの保守・改修

書いてあることは事実です。でもこれでは、あなたにしかない部分がひとつも書かれていません。

同じ業務でも、掘ればこういう経験が出てくることがあります。

// 掘り起こせる経験の例

  • ✓原因不明の障害を、ログとデータから追い切って再発防止まで持っていった
  • ✓手作業だった運用をスクリプト化して、月◯時間の作業を削減した
  • ✓仕様が固まっていない状態で、業務担当者に確認しながら実装を進めた
  • ✓レビューで後輩の設計ミスを事前に止めた
  • ✓古いライブラリのバージョンアップを、影響範囲を洗い出して実施した
社内では「当たり前の作業」でも、
別の会社では「課題を自分で定義して
解決した経験」として評価されます。

同じ経験が、書き方ひとつで別物になる。ここで差がつきます。

Solution

必要なのは学び直しの前に、
「経験の棚卸し」かもしれません

「今の経験では通用しない気がする」と感じたとき、多くの人はまず勉強を始めようとします。

もちろん学習は無駄になりません。ただ、実務経験が2年以上あるエンジニアの場合、先に手をつけたほうが効果が出やすいのは、たいてい棚卸しのほうです。

なぜなら——

  • 1すでに持っている経験は、今日から使える資産だから
  • 2資格や新しい言語の学習は、評価につながるまでに時間がかかるから
  • 3そもそも「何を学ぶべきか」は、狙う現場が決まってからでないと決められないから

具体的にやることは、この4つです。

// STEP 01 → 04

  • 1経験の棚卸し ── 何を、どこまで、なぜやったのかを分解する
  • 2言い換え ── 社内の言葉を、市場で評価される言葉に置き換える
  • 3狙う現場の特定 ── その経験が最も高く評価される領域を決める
  • 4選考対策 ── 面接で再現性を説明できる状態にする

これを一人でやるのが難しいのは、自分の仕事を「当たり前」だと思っている人ほど、棚卸しができないからです。

だからこそ、経験者向けのエージェントという選択肢があります。

FAQ

よくある質問

実務経験が2年ちょうどでも相談できますか？
TechGOは実務経験2年以上のITエンジニアが対象です。2年でも対象に含まれます。むしろ、キャリアの方向性がこれから決まる時期だからこそ、「いまの経験がどう見られるか」を早めに確認しておく意味があります。
資格もGitHubのポートフォリオもありません。不利になりませんか？
実務経験者の選考で見られるのは、まず「業務で何を、どこまで、なぜやったか」です。資格や個人開発は加点材料になり得ますが、それが無いことが即マイナスになるわけではありません。むしろ多くの人は、業務経験の中に書ける材料を持っているのに、それを言語化できていない状態です。その整理を一緒にやるのがエージェントの役割です。
保守・改修がメインで、設計や新規開発の経験がありません。
そういう相談は珍しくありません。保守・改修の中にも、障害の原因追跡、影響範囲の見極め、既存仕様の読解、業務担当者との折衝など、評価対象になる経験は含まれています。「何もない」と思っているものを分解するところから始められます。
在職中でも進められますか？
可能です。TechGOには土曜の1Day選考会があり、平日に時間を取りにくい方でも進めやすい形があります。模擬面接も回数制限がないため、自分のペースで準備できます。
相談したら、転職を強く勧められませんか？
「転職するかどうかを決めてから相談しなければならない」ということはありません。まずは自分の経験がどう評価されるかを聞いて、そのうえで動くかどうかを決める、という使い方もできます。相談は無料です。
Java（またはPython）以外の言語に変えないと年収は上がりませんか？
そうとは限りません。このページで見てきたとおり、条件に効いているのは言語の名前そのものよりも、その言語がどんな事業領域・どんな開発フェーズで使われているかです。同じ言語のまま、使われる場所を変えるという選択肢もあります。どちらが自分に合うかは、経験を整理してから判断するほうが確実です。
